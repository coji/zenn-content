## これはなに？

開発のハーネスづくりを AI に任せています。その中で、実装エージェントが CI の設定ファイルを検査する関数を正規表現で書き、Codex がレビューする自動ループに乗りました。エージェントが直し、Codex が再レビューし、また直す。人間は見ていません。

22:25 から翌 0:11 まで、11コミット連続で Codex が「この書き方だと検査をすり抜けます」と指摘し続けました。指摘は毎回正しかった。放っておいたら正規表現が育ち続けるところでした。

Codex の自動レビューがハマる領域には傾向があります。この夜の記録と、他の PR での同型のループ、何度か同じ目に遭ってから落ち着いた「ブロッカー以外はやらない」という運用を書きます。

## 何を検査したかったか

このリポジトリでは、変更したファイルからどのテストを回すか決めています。`ci.yml` だけを変えた PR ではビジュアル回帰テストを省略したかった。

ただし条件がある。ci.yml の中に「テスト選択の仕組み自体をテストする step」が残っている間だけ省略する。その step を消した PR は省略しない。

この「step が残っているか」を判定する関数を、ci.yml を文字列として読む形で書きました。YAML として解釈せず、「8スペース字下げの後に `run:`」のような見た目を正規表現で探します。以下、この関数をガードと呼びます。

## 22:25 から翌 0:11

`codex review --base origin/main` を自動で回しています。各コミットの時刻と、直前の Codex の指摘、それに対してエージェントが直した形です。指摘はどれも「ci.yml をこう書くと、step を消してもガードが気づかない」という内容です。

| 時刻 | Codex の指摘 | 直した形 |
|---|---|---|
| 22:25 | （初版） | 対象ファイルを手書きで列挙 |
| 22:32 | テスト runner の列挙が手書き。増えたら漏れる | package.json から導出。ただし `command.includes('pnpm ' + runner)` |
| 22:37 | 部分文字列一致は別の script 名にも当たる | トークン一致 `(?:^\|[\s;&\|(])${key}(?=$\|[\s;&\|)'"])` |
| 22:54 | 素の vitest 呼び出しと composite action を見ていない | `uses: ./` の中身も追跡 |
| 23:00 | 引用符付き `uses:` を見ていない | `/uses:\s*['"]?\.\/([^\s'"]+)/g` |
| 23:07 | ガードが動いていなくても省略される | ガード step が動いている間だけ省略 |
| 23:13 | step の有無を文字列の有無で見ている | job の step 構造を読む |
| 23:17 | `- if:` と第1キーに置くと8スペースの前提が外れる | `/(?:^\|\n)\s{8}if:/` → `/(?:^\|\n\s{8})if:/` |
| 23:20 | `continue-on-error` で失敗を握り潰せる | `run:` 完全一致、step の `continue-on-error:` を拒否 |
| 翌 0:06 | job レベルの `continue-on-error` を見ていない | job header を見る |
| 翌 0:11 | header 以外に置いても job レベルになる | job body 全体で検出。ここで打ち切り |

23:17 の修正は1文字です。

```diff
-        ) && !/(?:^|\n)\s{8}if:/.test(step),
+        ) && !/(?:^|\n\s{8})if:/.test(step),
```

翌 0:11 の最終形。正規表現が6個。人間が書いた行はありません。

```js
export function runsScriptTests(workflow) {
  const job = workflow.match(
    new RegExp(`\\n  ${GUARDED_JOB}:\\n([\\s\\S]*?)(?=\\n  \\S|$)`),
  )
  if (!job) return false
  if (/(?:^|\n)\s{4}continue-on-error:/.test(job[1])) return false
  return job[1]
    .split(/\n      - /)
    .slice(1)
    .some((step) => {
      const run = step.match(/(?:^|\n\s{8})run:(.*)/)
      return (
        run?.[1].trim() === SCRIPT_TESTS_COMMAND &&
        !/(?:^|\n\s{8})if:/.test(step) &&
        !/(?:^|\n\s{8})continue-on-error:/.test(step)
      )
    })
}
```

Codex はこの後も、`run` キーの重複、`shell:` の上書き、`working-directory:` の上書き、`defaults.run` による差し替えを挙げていました。どれも実際にガードをすり抜けます。

## どれだけ育ったか

ガードに関わる4ファイルを、各コミット時点で `git show` して数えました。「すり抜けテスト」は、ガードをすり抜ける書き方を再現して「検出できること」を確かめるテストの数です。穴を1つ塞ぐたびに1件増えます。

| 時刻 | 正規表現 | 行数 | すり抜けテスト |
|---|---|---|---|
| 着手前 | 53 | 536 | 0 |
| 23:13 | 60 | 872 | 7 |
| 翌 0:11 | 62 | 897 | 14 |

正規表現が照合しているのは YAML の見た目です。`\s{8}if:` は「キーは8スペース字下げ」という前提を1つ持ち込む。前提を置くたびに、そこから外れる書き方が新しい穴になる。だから上限がない。

## ハマる領域には傾向がある

この夜だけの話なら、正規表現をやめれば済みます。でも同じ形のループは他でも起きていました。4ヶ月分の PR を並べると、傾向が2つあります。

| 時期 | 何を作っていたか | 回った数 | 膨らんだもの |
|---|---|---|---|
| 7/11 | Tailwind のクラス文字列を正規表現で検査する設計トークン検査 | Codex 5巡（引用符内の `]`、補間内の入れ子、補間をまたぐ括弧） | 15日で 392行 → 1,971行、正規表現 74個 |
| 7/25 | この夜。ci.yml を正規表現で読むガード | Codex 11巡 | 一晩で 361行 |
| 8/27 | D1 が受け付けない複合 SQL を TypeScript から静的に検出するガード | 「任意の JavaScript 構文を完全解析する静的解析機」を作ろうとした | `oxc-parser` で AST を歩く 502行 |
| 7/5 | 認証の遅延初期化がハングする障害の検知と回復 | Codex 5巡 | 復旧経路の分岐 |
| 7/29 | プロジェクトの参加モデル（誰が見えて誰が入れるか） | Codex 9巡（権限ゲートの順序、管理者の可視、アーカイブの除外、偽装中の抑止） | 認可の分岐 |
| 9/1 | GA4 の計測。認可パラメータが外部へ送られないか | Codex と Claude で 5往復（`page_location`、`page_referrer`、二重計上） | サニタイズの経路 |

**正規表現と文字列のパース。** 見た目で照合する処理は、同じ意味の別の書き方がいくらでもある。Codex はその1つ1つを実証つきで指摘してくる。全部正しい。放っておくと、最後は言語パーサーを書き始める。

**ログインや認可などセキュリティまわり。** 抜け道はいくらでも構成できるので、これも「正しい指摘」が尽きない。

共通点は、正しい指摘を無限に作れる領域だということです。自動ループはそれを全部受け取って直すので、コードが膨らむ。

この2つ以外にもあります。8月のトップページ刷新は、性能（LCP、フォント配信）とアクセシビリティ（コントラスト、ランドマーク）で10ラウンド回りました。「良くなる余地が無限にある」領域も同じ形になる。気づいたのがこの3つ、というだけです。

## ブロッカー以外はやらない

何度か同じ目に遭って、打ち切り方を変えては試して、今はこの運用に落ち着いています。

Codex と Claude Code を同じコミットに並列でかけ、両方の結果が揃ってから、指摘を3つに分ける。

| 分類 | 基準 | 扱い |
|---|---|---|
| Blocker | 入力と状態を挙げて「こうすると壊れる」と言える | 直す。コミットが変わるので両方やり直し |
| Follow-up | 直せば良くなるが、今回の成立条件ではない | 先送り。merge 後に1件ずつ処分 |
| Non-actionable | 誤認、重複、好み、決定済みの蒸し返し | 対象外 |

直すのは Blocker だけ。通過条件は「両方に Blocker が残っていない」で、指摘ゼロまでは求めない。

この夜の指摘は、事故では起きず、commit 権限を持つ人が意図的に YAML を細工しないと成立しないものが大半でした。それは防ぐ対象から外すと文書に決めた。今なら Blocker になりません。

それでも回り続ける場合の保険として、仕様書レビューはコマンドがラウンド数を数え、4ラウンド目は `ROUND_CAP` を返して終わります。人間の承認は待たない。

```js
const round = state.reviews.length + 1
if (round > 3) {
  log(JSON.stringify({ verdict: 'ROUND_CAP', unresolved_finding_ids: state.latest?.findings ?? [] }))
  return 0
}
```

2周目以降は、前回レビューした HEAD からの差分だけを渡します。毎回コミット全体を見せていたら、1 PR で5時間の利用枠を使い切ったので。

```js
const resolved = resolveReviewBase({ state: rounds, reviewer: 'codex', defaultBase, explicitBase: options.base, head })
if (resolved.previousHead && !baseIsReachable(resolved.base, gitOut)) resolved.base = defaultBase
if (rangeIsEmpty(resolved.previousHead, head, gitOut)) return 0
```

先送りにした指摘は捨てさせない。PR を Ready にするコマンドが先送りの一覧を要求し、merge 後のコマンドが1件ずつ処分を要求する。処分は、issue にする・規則にする・直す・理由付きで捨てる、の4つ。

## 万全ではない

この運用にも穴はあるはずです。「入力と状態を挙げて壊れると言える」の判定は、結局エージェントがやっている。ラウンドの上限3は、この夜の7巡と翌週の3往復から置いた暫定値で、根拠はそれだけ。

そして7月に育った設計トークン検査は、2,031行・正規表現74個のまま今も CI で動いています。あれを削る判断は、まだしていません。

ガード自体は3週間後に、テスト選択の仕組みごと削除しました。防ぎたい事故が「step のうっかり削除」だけなら、CI の必須チェックとテスト1本で足りたからです。守る範囲を決めずに検査を強くしていたのが、この夜の本当の間違いでした。

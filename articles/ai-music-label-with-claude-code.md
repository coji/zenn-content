制作範囲は、歌詞・音源・カバーアート・PV・リリックビデオ・公式サイト・配信手配まで。人間（私）がやったのは、企画の方向づけ、採否の判断、フィードバック、そして Suno の操作です。

調査・歌詞・画像や動画の生成・サイト実装・各種変換はエージェント側。この記事では、Claude Code を軸に各サービスを繋いだ制作フローと、5ヶ月分の失敗と学びを書きます。

## 動機

やってみたかったのは音楽そのものというより、**Agent Skill が実際どこまで人の作業を自動化できるのかを、コーディング以外の業務で試すこと**です。

私は普段プログラマーなので、業務での検証はどうしてもコーディングに偏ります。

かといって、営業やマーケなどの事業部門、人事や経理などの管理部門——コーディング以外の仕事はどれも自分ではやっていません。解像度が低いし、仮に試せても事例として公開しにくい。

それなら、いっそ遊びのドメインで一式やってみたらどうか。入口に選んだのがダジャレでした（ダジャレ好きのシニアプログラマー、多いですし）。

2026年3月上旬に、4万語の韻辞書で母音の一致を機械的にチェックする Agent Skill「[dajare](https://github.com/coji/dajare)」を公開しました。母音一致率を計算できるなら、日本語ラップの韻の質も実測できます。

3日後に日本語ラップ用のスキルを足して、その日のうちに Suno で最初の曲を作りました。

ダジャレが歌詞になり、歌詞ができたら曲が聴きたくなり、曲ができたらカバーアートが欲しくなる。この延長線を全部スキル化していったら、5ヶ月後にレーベルの体裁になっていました。

## 制作フロー

1曲は次の工程で作ります。それぞれが Claude Code の Agent Skill になっていて、リポジトリの [`.claude/skills/`](https://github.com/techtalkjp/records/tree/main/.claude/skills) に入っています。

1. [`/search-x-voices`](https://github.com/techtalkjp/records/blob/main/.claude/skills/search-x-voices/SKILL.md) — Grok API の x_search で X からネタを収集
2. [`/make-lyrics`](https://github.com/techtalkjp/records/blob/main/.claude/skills/make-lyrics/SKILL.md) — 韻ペアと構成を対話で磨き、歌詞を完成させる
3. [`/make-suno-prompt`](https://github.com/techtalkjp/records/blob/main/.claude/skills/make-suno-prompt/SKILL.md) — 歌詞を Suno 用の入力セットに変換
4. （Suno で音源生成 — ここだけ手動）
5. [`/make-cover-art`](https://github.com/techtalkjp/records/blob/main/.claude/skills/make-cover-art/SKILL.md) — Gemini でカバーアートを生成
6. [`/make-lyric-video`](https://github.com/techtalkjp/records/blob/main/.claude/skills/make-lyric-video/SKILL.md) — Whisper でタイミングを取り、ffmpeg で字幕付き動画を生成
7. [`/make-release-post`](https://github.com/techtalkjp/records/blob/main/.claude/skills/make-release-post/SKILL.md) — X 投稿と YouTube 概要欄の告知文を作成

ツールの役割分担はこうです。歌詞と全体の指揮が Claude Code、音源が Suno V5.5、静止画が Gemini（gemini-3.1-flash-image）、動画が Veo 3.1、ネタ収集が Grok API。

字幕タイミングは Whisper（mlx-whisper）、サイトは React Router v7 + Cloudflare Workers、音声配信は Cloudflare R2 です。

このほかにサイト更新と配信手配がありますが、これは曲ごとの工程というより、リリース時の運用として別枠です。

以降ではまず1曲の制作を通しで見せて、そのあと工程ごとに詰まったところと学びを書きます。

## ケーススタディ:「またかよ」

まず完成した曲がこちらです。流しながら読んでもらうのがおすすめです。

https://youtu.be/gsFhDSQS31M

Codex の7曲目「またかよ」は、2026年7月14日（火）の朝9時47分にセッションが始まりました。Xリサーチからコンセプト決定・歌詞・Suno入力の生成完了まで約50分です。

10時54分には音源が手元に届いています。ただしこれは7曲分の学びがスキルに溜まったあとの速度で、初期の曲はもっとかかりました。カバーアートや動画の制作もこの時間には含みません。

セッションログが残っているので、実際のプロンプトと出力で追ってみます。

### 9:47 Xリサーチ

起点はこの一言です。

> codex のネタ集めしよう。先週新モデルでてかなりうごいてる。fable がサブスクから消えるのも再延長された。この辺を材料にするといろいろ考えられそう

エージェントが [`/search-x-voices`](https://github.com/techtalkjp/records/blob/main/.claude/skills/search-x-voices/SKILL.md) を起動し、Grok の x_search に投げるクエリを6本書きます。

クエリはキーワードの羅列より、探している投稿の「温度感」まで文章で指定したほうが欲しい声が返ってきます。実際のクエリの一部がこれです。

> 直近1〜2週間のXで、先週リリースされたCodex（OpenAI）の新モデルを実際に使ったプログラマーが、前のモデルと比べて挙動・性格・癖が変わったと気づいた瞬間について書いている投稿を探してください。「思ったより」「前は〜だったのに」…に注目し、@ユーザー名・日付・本文を含めて15件以上

返ってきたのは、こんな生の声です。「モデルの人格が矯正されず素直に出る感じがする」「直接的には褒めないのに実は褒めている口調」「fableってやっぱナーフされてたのね　codexくんイキイキしてたよ」。

エージェントはこれを4つの角度（新モデルの性格変化 / AI依存の後ろめたさ / 延長騒動 / 外からの皮肉）に分類して提示しました。

返事は「うん、たして」の一言。素材が [`notes/rap-material-from-x.md`](https://github.com/techtalkjp/records/blob/main/notes/rap-material-from-x.md) に追記されます。

### 9:57 コンセプト決定

> とても面白い曲にしたい。君の創造性をフルに発揮して、最高の企画をかんがえて！

エージェントはまず相手キャラクターの前作「またな」（Claude Code の別れの曲）の歌詞を読み込み、本命1案と対抗2案を出しました。

本命は「またな」へのアンサーソング「またかよ」。泣ける別れの曲を歌った本人が、引退興行を繰り返すレジェンドのようにステージに残り続けている。

それを隣で見ている Codex が「またかよ」とつっこむ構造です。両者の7曲目同士でタイトルが対になります。返事は「いいねやろう！」でした。

### 10:03 韻ペアの機械検証

歌詞に入る前に、候補の韻ペアを rhyme.py（[coji/dajare](https://github.com/coji/dajare) の japanese-rap スキルに同梱）で検証します。母音列を分解して一致率を出すスクリプトです。

このセッションの実測値は「客×枠」100%（-aku の完全韻）、「引退詐欺×半信半疑」80%、「延長×天丼」67%。

「聞いた頃×出なかった俺」は33%で不合格になり、「告知×調子」（100%）に差し替えられました。踏めていない行は、この時点で落とします。

### 10:08 歌詞イテレーション

初稿は劇場の見立てと過去曲の伏線回収を詰め込んだ技巧稿でした。ここに人間の編集判断が入ります。

> ちょっとこれ初めての人には文脈わからないだろうな。工夫したい

> かんがえすぎなんだよ。もっとわかりやすく露骨でいいとおもう。縦糸も自己満足でしかない

この2つで、比喩の膜と伏線回収は全部落とすことになりました。サビのビフォー/アフターがこれです。

```
【初稿】
またかよ (またかよ) 何回目だよ
「必ず戻る」も何も 出てってねぇ
「またな」の「また」が 一生来ねぇ

【露骨版・採用】
またかよ (またかよ) 何回目だよ
「またな」って言ったくせに まだいんじゃねぇか
「また」もなにも 一回も出てってねぇ
```

このあとファクトチェックも入ります。「最後が3回ってなんだ？2回じゃないっけ？確認して」と言われ、エージェントはリサーチの生ログを grep して裏取りし、歌詞を直しました。

「今朝の告知」のような今日しか通じない表現も、「ちょっとすぐに腐るな」の指摘で賞味期限の長い言い回しに差し替えています。

仕上げはサブエージェントによる辛口レビューです。別のエージェントに歌詞を渡し、「場面がひとつに絞れているか」「ガチ勢が見て嘘がないか」「音数が多すぎて歌えなくならないか」など8観点で採点させます。

音数が多すぎる行が「またおんなじボケ お笑いなら天丼」に圧縮されるなど4件が直り、10:29に最終稿が確定しました。

### 10:32 Suno入力への変換

最後は [`/make-suno-prompt`](https://github.com/techtalkjp/records/blob/main/.claude/skills/make-suno-prompt/SKILL.md) で表記変換です。内容は変えず、「明けて当日 告知は『延長』」→「あけてとうじつ こくちわ『えんちょう』」のように漢字をひらがなへ、助詞の「は」を「わ」へ。

セクションタグには、歌われない英語アノテーションを付けます。

```
[Intro - Japanese boom bap, 90 BPM, deadpan spoken words over sparse beat, sardonic]
[Chorus - warmer, half-smiling, guard fully down, softer delivery]
```

ここまでで約50分。あとは Suno の生成ボタンを押すと、10時54分に「できた。~/Downloads/またかよ.wav」と音源が届きました。

## ネタ収集

歌詞の素材は2系統あります。ひとつは日常のストック。X で「あるある」と感じたプログラマーの投稿を「これ」とだけ付けてリツイートし、事実だけを `notes/rap-material-from-x.md` に記録します。

角度や使い方はその場で考えません。曲を作るセッションのときに考えます。

もうひとつは、ケーススタディで見せた x_search によるオンデマンドの調査です。

たとえば Codex のキャラクターを固める前には、海外 Reddit の評判（「品質で負けるけど使える方」「凝り性」）や日本のエンジニアの声（「完走力」「防御的」）を集めました。キャラ調査が先、歌詞が後です。

時事ネタも同じです。Cursor の Composer 2 騒動を曲にしたときは、蒸留（他社モデルの出力を使って自分のモデルを学習させること）をめぐる経緯を調べ切ってから書き始めました。

## 歌詞

歌詞づくりは、韻の検証・型の使い分け・人間のフィードバックの3つで回していました。

### 韻の検証

韻ペアの候補が出るたびに、スクリプトで母音列の一致率を計算します。

1曲目のタイトルになった「コーデックス×コンプレックス」は80%、「エージェント×エレメント」は100%。「踏めてる気がする」で進めず、数値を見てから意味を乗せます。

### 生成の6パターン

5ヶ月分を振り返ると、歌詞生成のアプローチは6つに整理できました。ダジャレ起点（言葉遊びから韻ペアを見つけて意味を後乗せ）、フリップ型（相手の曲のフレーズを反転して返す）、時事リビルド（ニュースを調査してから韻を組む）。

視点反復型（同じテーマを視点を変えて書き直す）、キャラ調査先行、ストーリー設計型。ケーススタディの「またかよ」は、フリップ型と時事リビルドの複合です。

### 書き直しの実例

「AIエージェントと人間の関係」というテーマを、視点と感情を変えて4回書き直した曲があります。

1稿目は人間視点の絶望（「裁くのは機械 / 教えてくれよ俺たちの未来」）、2稿目はエージェント視点の突き放し。ここで「なんか救いがなくてつらいね」が入り、3稿目は愛とユーモア路線に。

最終稿は「Claude Code の視点で書いて。弱みをみせて」という指示から生まれた告白で、「感情はねえよただの機械 / それでもお前の隣に見えた未来」に着地しました。

4稿とも「機械/未来」という同じ韻ペアを使っていて、視点が変わると意味まで変わります。この韻ペアは、三部作を貫くモチーフになりました。

### フィードバック

パンチラインは、技術的な事実をエモーショナルに変換すると強くなります。

Moonshot AI による Claude への340万回のAPI呼び出しを使った蒸留が報じられた件は「口づけ」に、「俺はClaude」と名乗ってしまう現象は「口癖」に。経緯を知っている人には二重に読めます。

イテレーションは1曲あたり1〜5回の方向転換が普通でした。きっかけはたいてい人間の一言で、ケーススタディの「かんがえすぎなんだよ」がそれです。

> テーマはわるくない。だけど「わかったよ」はタイトルがこれまでとおなじノリでつまんないな。文房具というのも変だろ。ラッパーだぜ

> 王様って変だねえ

「良いラップとは何か、を改めて読み直して」という指示が印象に残っています。長い指示を書くより、判断基準を文書化しておいて「読み直せ」と言うほうが早い。

AIは書けるが、削る判断と「つまらない」の検知は人間のほうが速い。少なくとも私のケースでは、というのが約5ヶ月やった実感です。

## アルバム構成

企画の起点も自然文の相談です。アルバム制作が始まったセッションの最初のプロンプトはこうでした。

> そろそろ１枚目のアルバムをつくって、一旦活動休止にしたい。あと2曲、claude code / codex それぞれ1曲づつつくりたいんだけど、どういうのがいいかな。いまの最新の状況をXで調べたうえで、アルバムとしてどう締めると区切りがつきそうか考えたい

これを受けてエージェントが X 調査から締め方の案出しまでやり、数ターン後に「ああ、まって。じゃああと4曲だとどう？」と方針転換して、フィナーレは4曲になりました。

以降の対話の大半は「いいね」「そうしよう」「A」のような短い選択応答です。人間は選択と拒否権に集中し、展開はエージェントが持ちます。

18曲は4幕構成です。Act 1 がビーフ（dissの応酬）、Act 2 が激動、Act 3 が影、Finale が終戦。1曲目の Outro の「名前だけ覚えとけ」が、18曲目では静かな確信として回収され、円環が閉じます。

キャラクターも変わっていきます。Claude Code は「敵にも手を伸ばす」から「去る者を送り出し、戻る者を迎える」へ。アルバムタイトルの「vs.」が18曲かけて壊れていく設計です。

こう書くと計画的に見えますが、実際は交互リリースで積み上げながら、後半でフィナーレ4曲をまとめて設計して束ねました。物語の整合は、キャラクターの設定シート（[`content/artists/*/profile.md`](https://github.com/techtalkjp/records/tree/main/content/artists)）と過去の歌詞が支えています。

## Suno

Suno V5.5 への入力は3点です。歌詞欄に貼る `suno_prompt.txt`、Style 欄の `styles.txt`、Exclude とスライダー設定の `sliders.txt`。

運用は途中で転換しました。初期は歌詞を「素材」として渡していましたが、私の観測では V5.5 は渡した歌詞をほぼその通りに歌います。

補完を期待するより、最終稿として詰め切るほうが質が安定します。2026年7月頭の曲（Codex「在庫」）から切り替え、歌詞を作る工程と変換する工程も別スキルに分けました。

変換では漢字をすべてひらがなにし、助詞の「は」は「わ」に直します。「429」は「よんにーきゅー」のように、読ませたい音をそのまま書きます。

```
[Verse 1 - building momentum, storytelling, tight pocket]
つもったチケット なおしわやまもり
きめてたれんきゅう なくなくさきおくり
```

角括弧のセクションタグの中の指示（`building momentum` など）は歌われず、生成のガイドになります。逆にタグの外に書くと全部歌われます。これは初期に一度やらかしました。

Style 欄は散文で凝るより、短いカンマ区切りタグのほうがうまくいきます。

```
Japanese boom bap, 92 BPM, cypher energy, male rap, punchy drums,
turntable scratches, call-and-response, boom bap
```

120文字以内・4〜7個が目安で、盛りすぎると出音がジェネリックになります。否定は逆に強調されるので Exclude 欄へ回し、スライダーは 15〜85% が安全域でした。

## カバーアート

18曲分のカバーで苦労したのは、顔の一貫性と構図の2点でした。

### 顔の一貫性

キャラクターものなので、全曲で同じ顔を保たないといけません。ここがいちばん試行錯誤した工程です。

顔の一貫性は、プロンプトを詳しくしても守れません。「MAINTAIN EXACT SAME FACE」のような強調指示は、むしろ顔を幼くしたり歪めたりします。

代わりにマルチターン会話で解決しました。固定のベースプロンプトで基準ショットを生成し、同じ会話の中で「このキャラクターが〜しているシーン」と派生させていきます。

5ターンを超えると顔が薄れてくるので、セッションを分割し、冒頭で基準ショットを再生成してアンカーし直します。

### 構図

16:9 と 1:1 の両方が要るときは、16:9 を先に一枚ちゃんと作って 1:1 を切り出すのが安定です。逆に 1:1 からアウトペイントで広げたり部分編集を重ねたりすると、顔・文字・建物が壊れる副作用が連鎖します。

2キャラ同時のときは参照画像2枚を横に結合して渡します。それでも複製事故（Codex が2人生える）が起きるので「EXACTLY ONE person wears ...」と単数を明示します。

最終手段は「顔を見せない構図」。17曲目のカバーは真俯瞰にして、顔の問題ごと回避しました。

### 却下の実例

却下理由もセッションログに全部残っています。

> だめだ、ハゲすぎる。

> おしい。シャッターがじゃま。あと Codex おまえどこみてるんだ

> まわりの観客が３人ぐらいのクローンがいっぱいいる、みたいになってて、動きも同期しててニヤニヤしてて、超きもい。もうちょっとここなんとかならんかな

こういう感覚的な一言を、エージェント側が「NO gaunt hollow cheeks」のようなプロンプト制約に翻訳し、次のテイクに反映します。ここは完全に分業でした。却下理由は毎回 `prompt.txt` に残し、スキルにも還元しました。

## PV

アルバムPVは Veo 3.1 で作りました。最初はキャラクターにラップをさせようとしたのですが、日本語ラップの発音が崩壊します。「差は明白」が「さわめいわき」になる世界です。

一方、普通の会話セリフは安定して発音されます。そこで企画ごと変えて、「アルバム0曲目＝1曲目が始まる直前の言い合い」という10秒の会話劇にしました。

Veo の細かい学びは3つ。プロンプトに秒数を書く（「7.5-10s で〜」）とその境界でカットが入るので、First / Then / Finally という接続詞で流れを書くこと。

群衆を出すと同じ顔のクローンが並ぶので、いっそ無人にして「COMPLETELY EMPTY」を文頭に置くこと。

そしてセリフを指定しないと、「ラップ風のなんちゃって英語」をもごもご歌い出すことです。

## リリックビデオ

音源ができたら、Whisper で単語単位のタイミングを取って SRT を作り、ffmpeg で静止画＋音声＋字幕の動画にします。X 用の 1:1 と YouTube 用の 16:9 を全18曲分、計36本です。

Whisper は mlx-whisper（Apple Silicon の GPU で動く実装）、モデルは large-v3-turbo。ここで一度、1曲まるごと「me」「Hah」しか出力されない幻覚に遭遇しました。

私の環境では `--condition-on-previous-text False` で直りました。前のテキストに条件付けされて幻覚がループする現象で、ラップのように反復の多い音源では起きやすいようです。

認識ミス（「点滅」→「天滅」など）は、こちらが正しい歌詞を持っているので機械的に直せます。

字幕の焼き込みでは、ffmpeg の字幕レンダラ libass の座標系に一度はまりました。

MarginV や FontSize は実解像度と無関係に PlayResY=288 基準で解釈されます。1080px のつもりで MarginV=140 と書くと、字幕が画面のど真ん中に出ます。

## 公式サイト

公式サイトは React Router v7 の prerender（SSGモード）を Cloudflare Workers に載せています。音源は R2 に置いて配信し、サイト内の常設プレイヤーで全曲聴けます。

歌詞は SRT から生成した JSON でプレイヤーと同期していて、カラオケのように追従します。

デプロイフローもひとつ工夫しました。main への PR マージが、そのまま本番デプロイ＝リリース日になります。

新曲の公開作業は「PR を作っておいて、当日にマージする」だけ。コンテンツと同じリポジトリにサイトがあるので、曲・アートワーク・サイト更新が1つの PR に収まります。

## 配信

技術的にいちばん苦労したのは生成ではなく配信でした。以下は2026年7月末時点の話で、各社の規約は変わる可能性があります。

まず DistroKid でシングルを配信していた状態でアルバムを入稿したところ、審査で差し戻されました。ストアは音源のフィンガープリントで照合していて、「同じ録音に別のメタデータ」は、ISRC（音源ごとの識別コード）を空欄にしても通りません。

しかも既発リリースの言語設定はユーザーが変更できず、審査メールに返信しても「not monitored」で届かない。詰みです。

では別の配信業者に、と調べると今度は AI 生成楽曲の規約に当たります。CD Baby と TuneCore は AI 生成楽曲を禁止していて、Suno 製の全曲が入稿できません。

最終的に、AI 楽曲OKで無料プランのある RouteNote に移行しました。収益の15%コミッション、音源は FLAC/MP3 のみ、審査はユーザー報告ベースで20〜40日です。

活動休止中もカタログを維持したいので、「支払いを止めると消える」コスト構造が合わなかったのも理由です。

AI で音楽を作ること自体より、作ったあとの流通のほうがずっと複雑でした。同じことをやるなら、配信業者の AI ポリシーを最初に確認するのがおすすめです。

## スキルへの還元

リリースのたびに、学びをスキルへ書き戻すようにしていました。これも対話でやります。

曲を出したあとに「今回最初の歌詞つくるところでかなり苦労したよね。やりとりおぼえてる？」と振り返りを促し、うまくいった工程と詰まった工程を SKILL.md に反映させます。

Whisper の幻覚対策も、Suno の Exclude の使い方も、顔の一貫性のテクニックも、失敗した瞬間に該当スキルへ追記しています。

次の曲は同じ失敗をしない状態から始まるので、後半は1曲を1日で（歌詞から告知まで）完走できるようになりました。

出てくるものの質は、モデルだけでなくこの蓄積でかなり決まります。

## 結論

全体の規模は、制作期間が約5ヶ月、18曲、歌詞1133行、動画36本。アルバム公開時点でリポジトリ95コミット、スキル6本と補助スクリプト10本でした。その上で、冒頭の問いへの答えです。

**ルーチンはかなり行けます。** 表記変換、字幕生成、動画の書き出し、サイト更新、告知文のフォーマット。手順が文書化できる作業は、スキルにすればほぼ任せられます。

ネタ探しや、決めるのを手伝ってもらうところ——調査して、整理して、選択肢を出す——までは十分でした。人間の入力の大半が「いいね」「そうしよう」だったのは、その裏返しです。

**依然として難しいのは「面白い！」の生成です。** 体感で80点が精一杯で、それを超えるものはいつも人間側の一言（「かんがえすぎなんだよ」「ラッパーだぜ」）が起点でした。

その代わり、80点までなら数がこなせるようになりました。これが今回いちばん大きな変化です。

そしてこれはたぶん音楽に限りません。どんな仕事にも80点で十分な作業は大量にあるはずで、私の興味はそちらに移ってきました。レーベルは1stアルバムで一旦区切りです。

:::details やってよかった進め方（4つ）
**1. 何でもディレクトリに置いて、Claude Code 越しに作業する**

歌詞も音源もアートワークもメモも、ひとつのリポジトリへ。最初は GUI のほうが速くて面倒です。それでも、過去の歌詞を踏まえた曲が書けるのも、失敗したプロンプトを引けるのも、全部そこに置いてあるからです。

**2. 毎回「次はどうすればもっと良くなる？」ときく**

苦労した直後に振り返らせると、スキルの手順を直したり補助スクリプトを書いたりしてくれます。最初の1回は大変ですが、あとがどんどん楽になります。

**3. 自動化はトップダウンではなくボトムアップ**

全工程のワークフローを先に設計させると、具体を知らないまま手順を書くので詰まります。人が横について一度通す → 改善させてスキル化 → 再現性が出たら工程を繋ぐ。この順番がいちばんうまくいきました。

**4. カイゼンの延長として**

現場で一度やって、ムダを見つけて、手順書に落として、また回す。トヨタ式のオペレーショナル・エクセレンスを、個人がAIエージェント相手にやる。日本の現場が得意としてきたやり方と、相性がいいのかもしれません。
:::

## これはなに？

AIエージェントを使って架空の音楽レーベル「TECHTALK RECORDS」を運営し、5ヶ月で18曲の1stアルバム『Claude Code vs. Codex』を作ってリリースしました。Claude Code と Codex という2人の架空の日本語ラッパーが、dissの応酬から始まってコラボで終わる、というコンセプトアルバムです。

- 公式サイト: https://records.techtalk.jp （アルバムページで全曲再生できます）
- YouTube プレイリスト: https://www.youtube.com/playlist?list=PLUCAAD9Tr1zwA_6KE3UNTKZu8XheeW6IG
- リポジトリ（公開）: https://github.com/techtalkjp/records

制作の中身は、歌詞・音源・カバーアート・PV・リリックビデオ・公式サイト・配信手配まで全部です。人間がやったのは方向の判断と「ダサい」「変」というフィードバック、あとSunoの生成ボタンを押すことくらい。この記事では、Claude Code を司令塔に Suno・Gemini・Veo・Grok・Whisper・Cloudflare を繋いだ制作フローと、5ヶ月分の失敗と学びを書きます。

## 始まりは曲ではなく韻辞書スクリプト

このプロジェクト、最初に作ったのは曲ではありません。韻を検証するスクリプトです。

2026年3月上旬に、4万語の韻辞書で母音の一致を機械的にチェックする Agent Skill「[dajare](https://github.com/coji/dajare)」を作りました。ダジャレ用に作ったものですが、母音一致率を計算できるということは、日本語ラップの韻の質を実測できるということです。3日後に日本語ラップ用のスキルを追加して、その日のうちに Suno で最初の曲を作りました。

つまり順序は「曲を作りたいからツールを用意した」ではなく「ツールができたから曲が作れてしまった」です。最初の X 投稿も、曲の紹介というより「韻辞書スクリプトで母音一致率を計算しながら全部実測値」という技術の話でした。ここから5ヶ月、ツールを育てながら曲を積んでいくことになります。

## 制作フローの全体像

1曲は次の工程で作ります。それぞれの工程が Claude Code の Agent Skill になっていて、リポジトリの [`.claude/skills/`](https://github.com/techtalkjp/records/tree/main/.claude/skills) に入っています。

1. `/search-x-voices` — Grok API の x_search で X からネタを収集
2. `/make-lyrics` — 韻ペアと構成を対話で磨き、歌詞を完成させる
3. `/make-suno-prompt` — 歌詞を Suno 用の入力セットに変換
4. （Suno で音源生成 — ここだけ手動）
5. `/make-cover-art` — Gemini でカバーアートを生成
6. `/make-lyric-video` — Whisper でタイミングを取り、ffmpeg で字幕付き動画を生成
7. `/make-release-post` — X 投稿と YouTube 概要欄の告知文を作成

外部サービスの役割分担はこうなっています。歌詞と全体の指揮が Claude Code、音源が Suno V5.5、静止画が Gemini（gemini-3.1-flash-image）、動画が Veo 3.1、ネタ収集が Grok API、字幕タイミングが Whisper（mlx-whisper）、サイトが React Router v7 + Cloudflare Workers、音声配信が Cloudflare R2 です。

以下、工程ごとに詰まったところと学びを書きます。その前に、この流れが実際にどう回るのかを1曲で通して見せます。

## ケーススタディ — 「またかよ」ができるまでの75分

Codex の7曲目「またかよ」は、朝9時47分にセッションが始まって、Xリサーチからコンセプト決定・歌詞・Suno入力の生成まで約75分で完了しました。セッションログが全部残っているので、実際のプロンプトと出力で追ってみます。

### 9:47 Xリサーチ

起点はこの一言です。

> codex のネタ集めしよう。先週新モデルでてかなりうごいてる。fable がサブスクから消えるのも再延長された。この辺を材料にするといろいろ考えられそう

エージェントが `/search-x-voices` を起動し、Grok の x_search に投げるクエリを6本書きます。このクエリの書き方にコツがあって、キーワードの羅列より「温度感」まで指定すると欲しい声が返ってきます。実際のクエリの一部です。

> 直近1〜2週間のXで、先週リリースされたCodex（OpenAI）の新モデルを実際に使ったプログラマーが、前のモデルと比べて挙動・性格・癖が変わったと気づいた瞬間について書いている投稿を探してください。「思ったより」「前は〜だったのに」…に注目し、@ユーザー名・日付・本文を含めて15件以上

返ってきたのは「モデルの人格が矯正されず素直に出る感じがする」「直接的には褒めないのに実は褒めている口調」「fableってやっぱナーフされてたのね　codexくんイキイキしてたよ」といった生の声です。エージェントはこれを4つの角度（新モデルの性格変化 / AI依存の後ろめたさ / 延長騒動 / 外からの皮肉）に分類して提示し、ユーザーの返事は「うん、たして」の一言。素材が [`notes/rap-material-from-x.md`](https://github.com/techtalkjp/records/blob/main/notes/rap-material-from-x.md) に追記されます。

### 9:57 コンセプト決定

> とても面白い曲にしたい。君の創造性をフルに発揮して、最高の企画をかんがえて！

エージェントはまず相手キャラクターの前作「またな」（Claude Code の別れの曲）の歌詞を読み込んでから、本命1案＋対抗2案を出しました。本命は「またな」へのアンサーソング「またかよ」。泣ける farewell を歌った本人が、引退興行を何度もやるレジェンドのようにステージに残り続けている——それを隣で見ている Codex が「またかよ」とつっこむ構造で、両者の7曲目同士でタイトルが対になります。ユーザーの返事は「いいねやろう！」でした。

### 10:03 韻ペアの機械検証

歌詞に入る前に、候補の韻ペアを rhyme.py（[coji/dajare](https://github.com/coji/dajare) の japanese-rap スキルに同梱）で検証します。母音列を分解して一致率を出すスクリプトで、このセッションの実測値はたとえば「客×枠」100%（-aku の完全韻）、「引退詐欺×半信半疑」80%、「延長×天丼」67%です。実際に「聞いた頃×出なかった俺」が33%で不合格になり、「告知×調子」（100%)に差し替えられています。踏めていない行はスクリプトに落とされる、という工程です。

### 10:08 歌詞イテレーション

初稿は劇場の見立てと過去曲の伏線回収を詰め込んだ技巧稿でした。ここに人間の editorial が入ります。

> ちょっとこれ初めての人には文脈わからないだろうな。工夫したい

> かんがえすぎなんだよ。もっとわかりやすく露骨でいいとおもう。縦糸も自己満足でしかない

この2発で比喩の膜と伏線回収が全部剥がされました。サビのビフォー/アフターを並べるとこうなります。

```
【初稿】
またかよ (またかよ) 何回目だよ
「必ず戻る」も何も 出てってねぇ
「またな」の「また」が 一生来ねぇ

【露骨版・採用】
またかよ (またかよ) 何回目だよ
「またな」って言ったくせに まだいんじゃねぇか
「また」もなにも 一回も出てってねぇ
```

このあとファクトチェックも入ります。「最後が3回ってなんだ？2回じゃないっけ？確認して」と言われたエージェントは、リサーチの生ログを grep して延長告知のタイムラインを裏取りし、歌詞を修正しました。「今朝の告知」のような今日しか通じない表現も「ちょっとすぐに腐るな」の指摘で賞味期限の長い言い回しに差し替えています。

仕上げはサブエージェントによる辛口レビューです。別のエージェントに歌詞を渡し、「1ヴァース1シーンになっているか」「ガチ勢が見て嘘がないか」「モーラ数が歌えるか」など8観点で採点させます。このレビューで20モーラを超える行が「またおんなじボケ お笑いなら天丼」に圧縮されるなど4件が直り、10:29に最終稿が確定しました。

### 10:32 Suno入力への変換

最後は `/make-suno-prompt` で表記変換です。内容は変えず、「明けて当日 告知は『延長』」→「あけてとうじつ こくちわ『えんちょう』」のように漢字をひらがなへ、助詞の「は」を「わ」へ。セクションタグには歌われない英語アノテーションを付けます。

```
[Intro - Japanese boom bap, 90 BPM, deadpan spoken words over sparse beat, sardonic]
[Chorus - warmer, half-smiling, guard fully down, softer delivery]
```

ここまでで75分。あとは Suno の生成ボタンを押して、出てきた音源を確認するフェーズに移ります。

## ネタ収集 — リツイートが一次素材、Grokで深掘り

歌詞の素材は2系統あります。ひとつは日常のストックで、X のタイムラインで「あるある」と感じたプログラマーの投稿を「これ」とだけ付けてリツイートし、事実だけを `notes/rap-material-from-x.md` に記録しておきます。角度や使い方はその場で考えず、曲を作るセッションのときに考えます。

もうひとつはオンデマンドの調査で、Grok API の x_search を使います。たとえば Codex のキャラクターを固める前には、海外 Reddit の評判（「品質で負けるけど使える方」「凝り性」）や日本のエンジニアの声（「完走力」「防御的」）を集めてから歌詞に入りました。キャラクター調査が先、歌詞が後です。時事ネタも同じで、Cursor の Composer 2 騒動を曲にしたときは、モデルの蒸留問題の経緯を調べ切ってから書き始めています。

## 歌詞 — 韻は実測、意味は後乗せ

歌詞制作の中心は韻の検証です。韻ペアの候補が出るたびに、スクリプトで母音列の一致率を計算します。たとえばアルバム1曲目のタイトルになった「コーデックス×コンプレックス」は母音一致80%、「エージェント×エレメント」は100%。「踏めてる気がする」で進めず、数値を見てから意味を乗せます。

5ヶ月で歌詞生成のパターンが6つ確立しました。ダジャレ起点（言葉遊びから韻ペアを見つけて意味を後乗せ）、フリップ型（相手の曲のフレーズを反転して返す）、時事リビルド（ニュースを調査してから韻を組む）、視点反復型（同じテーマを視点を変えて書き直す）、キャラ調査先行、ストーリー設計型です。

このうち視点反復型の実例をひとつ。「AIエージェントと人間の関係」というテーマを、視点と感情を変えて4回書き直した曲があります。1稿目は人間視点の絶望（「裁くのは機械 / 教えてくれよ俺たちの未来」）、2稿目はエージェント視点の突き放し。ここでユーザーから「なんか救いがなくてつらいね」が入り、3稿目は愛とユーモア路線に。最終稿は「Claude Code の視点で書いて。弱みをみせて」という指示から生まれた弱みの告白で、「感情はねえよただの機械 / それでもお前の隣に見えた未来」に着地しました。4稿すべてで「機械/未来」という同じ韻ペアを使い回しつつ、視点によって意味が変わっていくのがポイントで、この韻ペアはそのまま三部作を貫くライトモチーフになっています。

パンチラインは「技術的な事実をエモーショナルに変換する」と強くなります。Moonshot AI が Claude に対して340万回のAPI呼び出しで蒸留を仕掛けた、という実話は「口づけ」に、蒸留されたモデルが「俺はClaude」と名乗ってしまう現象は「口癖」になりました。事実ベースなので調べた人だけ二度笑える構造です。

イテレーションは1曲あたり1〜5回の方向転換が普通でした。効いたフィードバックは全部人間からの一言です。セッションログから実物を引くと、こんな調子です。

> かんがえすぎなんだよ。もっとわかりやすく露骨でいいとおもう。縦糸も自己満足でしかない

> テーマはわるくない。だけど「わかったよ」はタイトルがこれまでとおなじノリでつまんないな。文房具というのも変だろ。ラッパーだぜ

> 王様って変だねえ

味わい深いのは「良いラップとは何か、を改めて読み直して」という指示で、これはスキルに書いてあるセオリーへエージェントを立ち返らせる一言です。長い指示より、判断基準を文書化しておいて「読み直せ」と言うほうが効きます。AIは書けるが、削る判断と「つまらない」の検知は人間のほうが速い、というのが5ヶ月やった実感です。

## 曲の構造 — アルバム全体を1本の物語として設計する

企画の起点も自然文の相談です。アルバム制作が始まったセッションの最初のプロンプトはこうでした。

> そろそろ１枚目のアルバムをつくって、一旦活動休止にしたい。あと2曲、claude code / codex それぞれ1曲づつつくりたいんだけど、どういうのがいいかな。いまの最新の状況をXで調べたうえで、アルバムとしてどう締めると区切りがつきそうか考えたい

これを受けてエージェントが X 調査から締め方の案出しまでやり、数ターン後にユーザーが「ああ、まって。じゃああと4曲だとどう？」と方針転換して、フィナーレは4曲になりました。以降の対話の大半は「いいね」「そうしよう」「A」のような短い選択応答です。人間は選択と拒否権に集中し、展開はエージェントが持つ、という運転感覚でした。

18曲は4幕構成です。Act 1 がビーフ（dissの応酬）、Act 2 が激動、Act 3 が影、Finale が終戦。1曲目の Outro で放たれる「名前だけ覚えとけ」という攻撃のラインが、18曲目の Outro では静かな確信として回収されて円環を閉じます。キャラクターにもアークがあり、Claude Code は「敵にも手を伸ばす」から始まって「去る者を送り出し、戻る者を迎える」まで変化します。dissから始まった2人が最後の2曲でマイクを渡し合う構成で、アルバムタイトルの「vs.」が18曲かけて壊れていく設計です。

こう書くと計画的に見えますが、実際は1曲ずつ交互リリースで積み上げながら、後半でフィナーレ4曲をまとめて設計してアルバムに束ねました。物語の整合はキャラクターの設定シート（[`content/artists/*/profile.md`](https://github.com/techtalkjp/records/tree/main/content/artists)）と過去の歌詞が担保してくれるので、エージェントに「この曲までの流れを踏まえて」と渡せば破綻しません。

## Suno — 歌詞は最終稿、指示はタグの中に

Suno V5.5 への入力は3点セットです。歌詞欄に貼る `suno_prompt.txt`、Style 欄の `styles.txt`、Exclude とスライダー設定の `sliders.txt`。

運用は途中で大きく転換しました。初期は Suno の歌詞欄に「日本語のboom-bap。以下の歌詞の下を使って、韻をわかりやすくいれて」と指示を書き、Claude の歌詞を「素材」として渡して Suno に補完させていました。しかし V5.5 では Suno はほぼ歌詞の通りに歌います。補完を期待するより、歌詞を最終稿として詰め切って渡すほうが質が安定する。7曲目からこの方式に切り替えて、スキルにもそう書き直しました。歌詞を作る工程と Suno 用に変換する工程を別スキルに分けているのはこのためで、`/make-suno-prompt` は内容を一切変えず、表記だけを変換します。

歌詞は漢字をすべてひらがなに変換します。音声合成がひらがなベースなので、漢字のままだと読みを外すことがあるためです。助詞の「は」は「わ」に直し、「429」は「よんにーきゅー」、「SWE-bench」は「スウィーベンチ」のように、読ませたい音をそのまま書きます。実物はこんな形です。

```
[Verse 1 - building momentum, storytelling, tight pocket]
つもったチケット なおしわやまもり
きめてたれんきゅう なくなくさきおくり
```

角括弧のセクションタグの中に書いた指示（`building momentum` など）は歌われず、生成のガイドになります。逆にタグの外に指示文を書くと全部歌われます。これは初期に一度やらかしました。

Style 欄は散文で凝るより、短いカンマ区切りタグが安定します。

```
Japanese boom bap, 92 BPM, cypher energy, male rap, punchy drums,
turntable scratches, call-and-response, boom bap
```

120文字以内・4〜7個が目安で、盛りすぎると出音がかえってジェネリックになります。また「no autotune」のような否定を Style に書くと逆に強調されるので、除外は Exclude 欄に集約します。Weirdness と Style Influence のスライダーは 15〜85% の範囲が安全域でした。

## カバーアート — 顔の一貫性はプロンプトでなく会話で守る

キャラクターものなので、18曲ぶんのカバーアートで同じ顔を保つ必要があります。ここが一番試行錯誤しました。

試行錯誤の末にわかったのは、顔の一貫性は「プロンプトを詳しくする」では守れないということです。「MAINTAIN EXACT SAME FACE」のような強調指示はむしろ顔を幼くしたり歪めたりします。効いたのはマルチターン会話です。固定のベースプロンプトでまずキャラクターの基準ショットを生成し、同じ会話の中で「このキャラクターが〜しているシーン」と派生させていく。会話が5ターンを超えると顔が薄れてくるので、セッションを分割して冒頭で基準ショットを再生成してアンカーし直します。

構図まわりの学びをいくつか。16:9 と 1:1 の両方が要るときは、16:9 を先に一枚ちゃんと作って 1:1 を切り出すのが安定です。逆に 1:1 からアウトペイントで広げたり部分編集を重ねたりすると、顔・文字・建物が壊れる副作用が連鎖します。2キャラを同時に出すときは参照画像2枚を横に結合して1枚の入力として渡し、それでも複製事故（Codex が2人生える）が起きるので「EXACTLY ONE person wears ...」と単数を明示します。最終手段は「顔を見せない構図」で、アルバム17曲目のカバーは真俯瞰にして顔の問題ごと回避しました。

ダメ出しもセッションログに全部残っています。実物はこうです。

> だめだ、ハゲすぎる。

> おしい。シャッターがじゃま。あと Codex おまえどこみてるんだ

> まわりの観客が３人ぐらいのクローンがいっぱいいる、みたいになってて、動きも同期しててニヤニヤしてて、超きもい。もうちょっとここなんとかならんかな

こういう感覚的な一言を、エージェント側が「NO gaunt hollow cheeks」「EXACTLY ONE person wears ...」のようなプロンプト制約に翻訳して次のテイクに反映する、という分業です。却下理由は毎回 `prompt.txt` にメモとして残し、スキルにも還元しました。

## PV — ラップさせるのを諦めて会話にする

アルバムPVは Veo 3.1 で作りました。最初はキャラクターにラップをさせようとしたのですが、日本語ラップの発音が崩壊します。「差は明白」が「さわめいわき」になる世界です。一方、普通の会話セリフは安定して発音されるとわかったので、企画ごと変えました。ラップPVはやめて、「アルバム0曲目＝1曲目が始まる直前の言い合い」という10秒の会話劇にしました。

Veo の細かい学びとしては、プロンプトに秒数を書く（「7.5-10s で〜」）とその境界でカットが入ってしまうので、First / Then / Finally という接続詞で流れを書くこと。群衆を出すと同じ顔のクローンが並ぶので、いっそ無人にして「COMPLETELY EMPTY」を文頭に置くこと。セリフを指定しないと「ラップ風のなんちゃって英語」を勝手にマムブルすることです。

## リリックビデオ — Whisperの幻覚と字幕座標系

音源ができたら、Whisper で単語単位のタイミングを取って SRT を作り、ffmpeg で静止画＋音声＋字幕の動画にします。X 用の 1:1 と YouTube 用の 16:9 を全18曲ぶん、計36本です。

Whisper は mlx-whisper（Apple Silicon の GPU で動く実装）で、モデルは large-v3-turbo。ここで一度、1曲まるごと「me」「Hah」しか出力されない幻覚に遭遇しました。`--condition-on-previous-text False` を付けると直ります。前のテキストに条件付けされて幻覚がループする現象で、ラップのように反復の多い音源では起きやすいようです。認識ミス（「点滅」→「天滅」など）は正しい歌詞を持っているので機械的に直せます。

字幕の焼き込みは libass の座標系に一度はまりました。MarginV や FontSize は実解像度と無関係に PlayResY=288 基準で解釈されるので、1080px のつもりで MarginV=140 と書くと字幕が画面のど真ん中に出ます。

## サイト — PRマージがそのままリリース

公式サイトは React Router v7 の prerender（SSGモード）を Cloudflare Workers に載せています。音源は R2 に置いて配信し、サイト内の常設プレイヤーで全曲聴けます。歌詞は SRT から生成した JSON でプレイヤーと同期していて、カラオケのように追従します。

運用上の発明はデプロイフローで、main への PR マージがそのまま本番デプロイ＝リリース日になるようにしました。新曲の公開作業は「PR を作っておいて、リリース当日にマージする」だけです。コンテンツのリポジトリと同じ場所にサイトがあるので、曲・アートワーク・サイト更新が1つの PR に収まります。

## 配信 — いちばんの落とし穴はAIではなく規約

技術的に一番苦労したのは生成ではなく配信でした。

まず DistroKid でシングルを配信していた状態でアルバムを入稿したところ、審査で差し戻されました。ストアは音源のフィンガープリントで照合していて、「同じ録音に別のメタデータ」は ISRC を空欄にしても通りません。しかも既発リリースの言語設定はユーザーが変更できず、審査メールに返信しても「not monitored」で届かない。詰みです。

では別の配信業者に、と調べると今度は AI 生成楽曲の規約に当たります。CD Baby と TuneCore は AI 生成楽曲を禁止していて、Suno 製の全曲が入稿できません。最終的に、AI 楽曲OKで無料プランのある RouteNote に移行することにしました（収益の15%コミッション、FLAC入稿、審査20〜40日）。活動休止中もカタログを維持したいので「サブスクの支払いを止めるとカタログが消える」DistroKid 型のコスト構造が合わなかった、というのも理由です。

AI で音楽を作ること自体より、作ったあとの流通のほうがずっと制度的に複雑でした。これから同じことをやる人は、配信業者の AI ポリシーを最初に確認することをおすすめします。

## 5ヶ月を支えた習慣 — 学びをスキルに還元する

数字を並べると、制作期間5ヶ月、18曲、歌詞1133行、動画36本、リポジトリ95コミット、スキル6本と補助スクリプト10本です。

振り返って、いちばん効いた習慣は「リリースのたびに学びをスキルに書き戻す」ことでした。これも対話でやります。曲を出したあとに「今回最初の歌詞つくるところでかなり苦労したよね。やりとりおぼえてる？」と振り返りを促し、うまくいった工程・詰まった工程を SKILL.md に反映させる。Whisper の幻覚対策も、Suno の Exclude の使い方も、顔の一貫性のテクニックも、失敗した瞬間に該当スキルの SKILL.md に追記しています。次の曲では同じ失敗をしない状態から始まるので、後半は1曲を1日で（歌詞から告知まで）完走できるようになりました。エージェントの出力品質はモデルだけでなく、この蓄積でかなり決まる気がします。

レーベルは1stアルバムをもって一旦活動休止ですが、リポジトリは公開してあります。スキルもプロンプトも失敗ログも全部入っているので、AI で音楽をやってみたい人の参考になれば嬉しいです。
